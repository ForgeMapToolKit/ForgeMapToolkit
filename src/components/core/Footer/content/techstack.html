Tech Stack

ForgeMapToolkit runs as a native desktop application rather than a web app. Advanced mapping requires direct filesystem access to the game install, binary parsing of .scmap files, and writing output straight into the maps folder. None of that is possible from a browser sandbox, so the app is built on a stack that bridges native OS access with a full browser rendering engine for the UI.

Core Stack

Layer Choice Why
Desktop runtime Electron Bundled Node.js handles the binary .scmap parser, DDS encode and decode, SCD and ZIP scanning, and direct writes to the maps folder. Bundled Chromium keeps canvas rendering consistent across every user's Windows version.
UI framework React 18 Handles deeply nested, performance-sensitive state such as the 500-unit library, the 60fps Bézier curve editors in the Skybox Generator, and the Poisson disk sampling used for prop and emitter placement.
Build tool Vite Instant hot module replacement means library and canvas state survive a rebuild. A full library scan takes around 30 seconds, so losing that state on every code change would make development painful.

Architecture

The main process, running Node.js, owns everything filesystem and binary related. This includes the custom scmap.js parser, SCD archive scanning, DDS conversion, and settings storage. The renderer process, running React inside Chromium, owns all UI state. The two communicate over more than twenty IPC channels, which keeps the UI responsive during long operations like a full library scan and keeps binary parsing isolated from the rendering process.

Alternatives like Tauri, NW.js, and Python with PyQt were considered and set aside. Tauri would require rewriting the existing binary parsing and placement algorithms in Rust for marginal binary size savings, and its system WebView is less consistent across Windows versions than Electron's bundled Chromium. The reasoning behind each decision is documented in full for contributors.
